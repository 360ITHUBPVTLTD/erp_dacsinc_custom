01 · Overview

Overview

What the company does, what the system is for, and how the pieces fit.

The business

Dac's Inc supplies uniforms and garments to corporate and institutional customers (hotels, restaurants, schools, hospitals) and runs retail POS stores. Customer orders are filled in two ways — trade items bought and resold, and BOM items made by outside jobbers (the company buys the fabric and trims, sends them to the jobber and receives finished garments). Pieces or panels can also go to embroidery jobbers.

Sales

Orders & approvals

CRM, Sales Orders, merchandiser and final approval.

Supply

Buy & make

Raw material, purchase, subcontracting, embroidery.

Fulfil

Pick, dispatch, bill

Pick List → Delivery Note → Sales Invoice → logistics.

Retail

POS stores

Shifts, billing, cash drawer, store stock.

What the system solves

  • One order tracked end to end on one dashboard (Order Flow), with the next action for each order.
  • No cross-order leaks — material bought for one order is never used by another.
  • No over-ordering, no duplicates — purchases capped at each order line's need; one draft per source line.
  • Approvals — merchandiser, then a named final approver.
  • Controlled visibility — merchandisers see their orders, stores their store, master data stays inside.
  • Store cash control — counted every shift, carried to the next, reported.
  • One agreed access sheet — the client signs off who may do what; saving applies it.

04 · Business Requirements (BRD)

BRD — what the business needs

Each requirement states the problem, what the business needs, how we know it is met, and its status. Click one to open it.

Objectives
  • Deliver every order on time with the right material, without one order consuming another's stock.
  • One place (Order Flow) for every team to see what is pending and act.
  • Buy only what orders need — never twice.
  • Control store cash and stock every shift.
  • Keep customer, supplier and price data inside the company.
  • Access agreed in writing with management.
Scope & stakeholders

In scope: CRM → Sales Order → approvals → planning → purchase → subcontracting → embroidery → picking → dispatch → invoice → logistics; POS stores; access control; mobile-app integration.

Standard ERPNext (not customised): general ledger, taxes, payroll, payment engine.

Stakeholders: Management · Sales/CRM · Merchandisers · Purchase · Production · Warehouse & Packing · Accounts & Finance · Logistics · Stores · HR · 360 IT Hub.

05 · Functional Requirements (FRD)

FRD — how the system does it

Each function: who uses it, where (screen), what happens, the rules, how to check it, and the code that enforces it (for developers).

Non-functional requirements

  • One count everywhere — screens answering the same question use the same server function, so no screen shows one number and another a different one.
  • Server-side rules — every rule is checked on the server; screens only explain.
  • Precision — raw-material checks use the stock precision (3 decimals).
  • Performance — company-wide lists are computed in batches, not row by row.
  • Real time — Order Flow and the Sales Order refresh when a linked document changes.

07 · Developer guide

Developer guide

How the code is organised, the conventions, and how to test safely.

Repositories

  • Bench root — a small Git repo for project scaffolding only (CLAUDE.md, CONTEXT.md, docs/, .scratch/). Never git add -A there.
  • Each app in apps/ is its own Git repo — do Git work inside the app. erp_dacsinc_custom → GitHub organisation 360ITHUBPVTLTD.
  • Developer copy — a local site restored from a live backup; never test on live.

Conventions

  • Docs in the same change: update docs/*.md — and this guide when a flow, role, rule or task status changes.
  • One rule, one function: screens answering the same question call the same server function.
  • Scope by sales order: every demand / supply figure is keyed by (item, warehouse, sales order).
  • Vendor apps: never edit silently — record in docs/core-modifications.md.
  • Fields from code: create_custom_fields in after_migrate or exported custom/*.json; removals need a patch.
  • Issues & specs: local markdown in .scratch/<feature>/ (not GitHub Issues).

Testing

  • Rolled-back scripts with bench --site <site> execute; suites in .scratch/order-flow-strict-rules/.
  • Always stub frappe.db.commit — saving Admin Settings commits, so rollback alone won't undo it.
  • Browser checks with headless Chrome and a temporary session.
  • After a planning change, compare the SO RM table, PO prompt and SCO dialog on the same data — they must agree.

Pitfalls

  • picked_qty, MR ordered_qty, subcontracted_quantity move only on submit — net drafts by hand.
  • ERPNext clears Purchase Order Item.bom on save — use the SO line's bom_no.
  • Query reports bypass permission hooks — POS reports are scoped separately.
  • frm.set_intro adds to the message area — clear it first. Form scripts need a hard refresh.
Never share site_config.json (passwords, encryption key); never run bench migrate, git reset --hard, git clean, commit or push for someone without being asked.
08 · Deploy & operations

Deploy & operations

How a change reaches live, and what to check afterwards.

What runs on migrate

  • Patches (once per site): access sheet set-up and apply, POS store scope, user roles from the client sheet, HR profile, party defaults, POS clean-up of stale shifts, and others.
  • after_migrate (every migrate): cash-drawer fields, access-sheet sync from access/agreed_access.json, Order Flow page roles, final approver role, procurement / logistics / embroidery fields, store names, flagged profiles.
  • Customisations from custom/*.json. Sync never deletes fields.

Safe read-only checks

  • stock_hold.report_missing — stock claimed but missing.
  • user_role_sheet.apply(dry_run=True) — what the user-role sheet would change.
  • pos_cash.close_stale_shifts(dry_run=True) — what the POS clean-up would do.

Older pages that differ

Process flow & diagram (Aug 2026) are older:
  • They show direct billing from the Pick List (Sales Invoice with Update Stock) — now refused: Pick List → DN → SI only.
  • They create a Pick List on SO submission — now when stock is available (Create Pick List).
  • They count pending MRs / POs as raw material for a Subcontract PO — now only material on the shelf, bought for the order or free.
  • They use team names; the ERP roles are in the Roles tab.
